# dev環境 疎通確認手順（T1-7 / マイルストーンM1）

CDKでデプロイしたインフラが設計どおりに動いているかを、コマンドで一つずつ確認する手順書。

**確認したいこと（マイルストーンM1の定義）**

1. Cognitoでユーザーを登録・ログインできる
2. 認証されていないリクエストはAPI Gatewayが弾く（Lambdaに到達しない）
3. 認証されたリクエストはLambdaまで届き、応答が返る
4. アクセスログがCloudWatchに出力される

対応設計書: [API共通設計](../../01_docs/02_sd/02_API設計/API共通設計.md) §2, §9 / [認証・認可設計](../../01_docs/02_sd/04_共通設計/認証・認可設計.md) / [ログ・監視設計](../../01_docs/02_sd/04_共通設計/ログ・監視設計.md)

## 前提

- `13_infra` のデプロイが完了していること（`cdk deploy -c env=dev --all`）
- AWS CLI v2 が使えること（`aws sts get-caller-identity` が通る）
- シェルは Git Bash / bash を想定（PowerShellの場合は変数代入の書き方が変わります）

> **Git Bash（MINGW64）を使う場合の注意**
> Git Bash は `/aws/apigateway/...` のような**スラッシュ始まりの引数をWindowsパスに自動変換**します（`C:/Program Files/Git/aws/...` のように書き換わる）。STEP 9 のCloudWatch Logs関連コマンドがこれに該当し、そのまま実行すると次のエラーになります。
>
> ```
> InvalidParameterException: Value at 'logGroupName' failed to satisfy constraint:
> Member must satisfy regular expression pattern: [\.\-_/#A-Za-z0-9]+
> ```
>
> 作業開始時に次を実行して自動変換を無効化しておいてください（このシェルの間だけ有効）。
>
> ```bash
> export MSYS_NO_PATHCONV=1
> ```

> **本手順で使うテスト用クライアントについて**
> アプリ用のUser Pool Client（`oracle-master-app-spa-dev`）はSRP認証のみを許可しているため、CLIから直接IDトークンを取得できません。そのため **dev環境限定** で、パスワード直接認証を許可した確認専用クライアント `oracle-master-app-cli-test-dev` をCDKで別途作成しています（`lib/stacks/auth-stack.ts`）。stg/prodには作成されません。アプリ実装からは使用しないでください。

### 事前チェック: 確認用クライアントがデプロイ済みか

```bash
aws cognito-idp list-user-pool-clients --user-pool-id $(aws cloudformation describe-stacks --stack-name OracleMasterApp-dev-Auth --query "Stacks[0].Outputs[?OutputKey=='UserPoolId'].OutputValue" --output text) --query "UserPoolClients[].ClientName" --output text
```

`oracle-master-app-cli-test-dev` が表示されない場合は、先に Auth スタックをデプロイしてください（差分はクライアント1つとスタック出力1つの追加のみで、既存リソースには影響しません）。

```bash
npx cdk deploy -c env=dev OracleMasterApp-dev-Auth
```

これを飛ばすと STEP 0 の `CLIENT=` が空になり、STEP 5 が `Invalid length for parameter ClientId, value: 0` で失敗します。

## STEP 0: スタック出力を環境変数に取り込む

**コマンド**

```bash
export AWS_REGION=ap-northeast-1
export API_ENDPOINT=$(aws cloudformation describe-stacks --stack-name OracleMasterApp-dev-Api --query "Stacks[0].Outputs[?OutputKey=='ApiEndpoint'].OutputValue" --output text | sed 's:/*$::')
export USER_POOL_ID=$(aws cloudformation describe-stacks --stack-name OracleMasterApp-dev-Auth --query "Stacks[0].Outputs[?OutputKey=='UserPoolId'].OutputValue" --output text)
export CLI_CLIENT_ID=$(aws cloudformation describe-stacks --stack-name OracleMasterApp-dev-Auth --query "Stacks[0].Outputs[?OutputKey=='CliTestClientId'].OutputValue" --output text)
echo "API=$API_ENDPOINT" && echo "POOL=$USER_POOL_ID" && echo "CLIENT=$CLI_CLIENT_ID"
```

**何をしているか**
デプロイ済みCloudFormationスタックの出力値（Outputs）から、APIのURL・User Pool ID・確認用クライアントIDを取得して環境変数に入れています。値をコピペして回らずに済むようにするための準備です。末尾の `sed` はAPIのURL末尾のスラッシュを取り除いており、以降 `$API_ENDPOINT/qualifications` の形で組み立てられるようにしています。

**正常な結果**

```
API=https://xxxxxxxxxx.execute-api.ap-northeast-1.amazonaws.com/dev
POOL=ap-northeast-1_xxxxxxxxx
CLIENT=xxxxxxxxxxxxxxxxxxxxxxxxxx
```

3行すべてに値が入っていること。空欄がある場合は、そのスタックがデプロイされていないか、`CliTestClientId` 出力を追加した後のデプロイが済んでいません。

## STEP 1: 認証なしのリクエストが拒否されること

**コマンド**

```bash
curl -i "$API_ENDPOINT/qualifications"
```

**何をしているか**
`Authorization` ヘッダを付けずにAPIを呼びます。API GatewayのCognitoオーソライザーが、Lambdaを呼び出す前にリクエストを弾くことを確認します。参照系APIにも認証を必須とする設計（API共通設計 §2）が実際に効いているかの確認です。

**正常な結果**

```
HTTP/1.1 401 Unauthorized
Content-Type: application/json
x-amzn-ErrorType: UnauthorizedException

{"message":"Unauthorized"}
```

`401` かつ `x-amzn-ErrorType: UnauthorizedException` が返ること。これが `200` を返す場合、そのエンドポイントにオーソライザーが付いていないことを意味するため、設計違反として調査が必要です。

---

## STEP 2: 不正なトークンが拒否されること

**コマンド**

```bash
curl -i -H "Authorization: Bearer invalid.token.value" "$API_ENDPOINT/qualifications"
```

**何をしているか**
デタラメな文字列をトークンとして送ります。「ヘッダが付いてさえいれば通る」といった実装ミスがないこと、つまりトークンの署名検証が実際に行われていることを確認します。

**正常な結果**

STEP 1 と同じく `401 Unauthorized` / `{"message":"Unauthorized"}`。

## STEP 3: テストユーザーを作成する

**コマンド**

```bash
aws cognito-idp admin-create-user \
  --user-pool-id "$USER_POOL_ID" \
  --username test-m1@example.com \
  --user-attributes Name=email,Value=test-m1@example.com Name=email_verified,Value=true Name=name,Value=疎通確認ユーザー \
  --message-action SUPPRESS
```

**何をしているか**
確認用のユーザーをCognitoに直接作成します。

- `--message-action SUPPRESS` … 招待メールを送信しません。存在しないアドレスへの送信を避けるためです
- `Name=email_verified,Value=true` … メール確認を済ませた状態にします。通常のサインアップでは確認コード入力（S-02）に相当する部分を省略しています
- `Name=name,Value=...` … 表示名。`GET /users/me` が `OR_M_USER` レコードを自動作成する際に `name` クレームから `displayName` を取得する設計（API-10）のため、ここで設定しておきます

**正常な結果**

`User` オブジェクトのJSONが返り、その中に次が含まれること。

```json
"UserStatus": "FORCE_CHANGE_PASSWORD"
```

この時点ではまだログインできません（次のSTEPでパスワードを確定させます）。なお、このUser Poolはメールアドレスをログイン識別子にしているため、レスポンスの `Username` にはCognitoが採番したUUIDが入ります。以降のコマンドではメールアドレスをそのまま指定して構いません。

## STEP 4: パスワードを確定する

**コマンド**

まずパスワードを環境変数 `TEST_PASSWORD` に入れます。次の1行をそのまま実行してください。

```bash
read -rsp 'パスワードを入力してEnter: ' TEST_PASSWORD; echo
```

> **`read` の使い方（要注意）**
> クォート内の `パスワードを入力してEnter: ` は**画面に表示される案内文**であり、ここにパスワードを書くのではありません。コマンドを実行するとカーソルが止まるので、**その状態でパスワードをタイプしてEnter**を押します。`-s` オプションにより入力文字は画面に表示されません。この方法だとパスワードがシェルの履歴に残りません。

入力できたか確認します。

```bash
echo "文字数: ${#TEST_PASSWORD}"
```

`文字数: 0` と出た場合は変数が空です（案内文の位置にパスワードを書いてしまった、または何も入力せずEnterした）。もう一度 `read` からやり直してください。

`read` が扱いにくい場合は、引用符の中身を自分のパスワードに置き換えて直接代入しても構いません。ただしシェル履歴に残ります。

```bash
export TEST_PASSWORD='ここに実際のパスワードを書く'
```

変数に入ったら、User Pool 側に反映します。

```bash
aws cognito-idp admin-set-user-password \
  --user-pool-id "$USER_POOL_ID" \
  --username test-m1@example.com \
  --password "$TEST_PASSWORD" \
  --permanent
```

**何をしているか**
初期パスワードの強制変更状態を解除し、ログイン可能な状態にします。`--permanent` を付けないと再び変更要求状態のままになります。パスワードは変数 `$TEST_PASSWORD` に保持し、STEP 5 でもそのまま使うため、**同じシェルで作業を続けてください**（別のターミナルを開くと変数が消えます）。

パスワードの条件:

- **8文字以上・英大文字・英小文字・数字を含む**（認証・認可設計 §4 のポリシー）
- **カンマ `,` を含めない**（STEP 5 で `USERNAME=...,PASSWORD=...` とカンマ区切りで渡すため）

> **注意:** 実在するパスワードをこのファイルやコミットに書き込まないでください。上記の `read` を使えばコマンド履歴にも残りません。

**正常な結果**

出力は何も表示されません（終了コード0）。エラーメッセージが出なければ成功です。ポリシー違反の場合は `InvalidPasswordException` が返ります。

## STEP 5: IDトークンを取得する

**コマンド**

```bash
export ID_TOKEN=$(aws cognito-idp admin-initiate-auth \
  --user-pool-id "$USER_POOL_ID" \
  --client-id "$CLI_CLIENT_ID" \
  --auth-flow ADMIN_USER_PASSWORD_AUTH \
  --auth-parameters USERNAME=test-m1@example.com,PASSWORD="$TEST_PASSWORD" \
  --query "AuthenticationResult.IdToken" --output text)
echo "${ID_TOKEN:0:30}..."
```

**何をしているか**
メールアドレスとパスワードでCognitoにログインし、IDトークン（JWT）を取り出して環境変数に格納します。これが実際のアプリでログイン成功時にブラウザが受け取るものと同じ種類のトークンです。`--query` でIDトークンだけを抜き出しています。パスワードは STEP 4 で設定した `$TEST_PASSWORD` をそのまま参照するため、**このコマンドは書き換えずにそのまま実行できます**。

別のターミナルで再開するなどして `$TEST_PASSWORD` が消えている場合は、先に入れ直してください。

```bash
read -rsp 'テスト用パスワードを入力: ' TEST_PASSWORD; echo
```

**正常な結果**

```
eyJraWQiOiJ...
```

`eyJ` で始まる文字列が表示されること。`None` と表示された場合はログインに失敗しています（パスワード誤り、または認証フローが許可されていないクライアントIDを指定している）。

中身を確認したい場合は次のコマンドでペイロードをデコードできます。`sub`・`email`・`name` が入っていれば正常です。

```bash
echo "$ID_TOKEN" | cut -d. -f2 | base64 -d 2>/dev/null | tr ',' '\n'
```

## STEP 6: 認証ありでLambdaまで到達すること

**コマンド**

```bash
curl -i -H "Authorization: Bearer $ID_TOKEN" "$API_ENDPOINT/qualifications"
```

**何をしているか**
STEP 5で取得したトークンを付けて、STEP 1とまったく同じURLを呼びます。オーソライザーを通過し、ダミーLambdaが実行され、Cognitoのクレームがちゃんとバックエンドまで渡っていることを確認します。

**正常な結果**

```
HTTP/1.1 200 OK
Content-Type: application/json

{"message":"Hello from Oracle Master App (placeholder)","method":"GET","path":"/qualifications","sub":"xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"}
```

見るべきポイントは3つです。

| 項目 | 期待値 | 意味 |
|---|---|---|
| ステータス | `200` | オーソライザーを通過してLambdaが実行された |
| `path` | 呼び出したパスと一致 | ルーティングが正しい |
| `sub` | UUIDが入っている（`null` でない） | Cognitoのユーザー識別子がLambdaまで渡っている。これが取れることは、以降の実装で「自分のデータだけ操作させる」認可（認証・認可設計 §2.2）の前提になる |

## STEP 7: Phase1の全エンドポイントを確認する

**コマンド**

```bash
for path in qualifications categories questions users/me; do
  printf "%-20s GET  -> %s\n" "$path" "$(curl -s -o /dev/null -w '%{http_code}' -H "Authorization: Bearer $ID_TOKEN" "$API_ENDPOINT/$path")"
done
for path in questions/random sessions; do
  printf "%-20s POST -> %s\n" "$path" "$(curl -s -o /dev/null -w '%{http_code}' -X POST -H "Authorization: Bearer $ID_TOKEN" -H 'Content-Type: application/json' -d '{}' "$API_ENDPOINT/$path")"
done
printf "%-20s GET  -> %s\n" "sessions/{id}" "$(curl -s -o /dev/null -w '%{http_code}' -H "Authorization: Bearer $ID_TOKEN" "$API_ENDPOINT/sessions/dummy-id")"
printf "%-20s PUT  -> %s\n" "sessions/{id}" "$(curl -s -o /dev/null -w '%{http_code}' -X PUT -H "Authorization: Bearer $ID_TOKEN" -H 'Content-Type: application/json' -d '{}' "$API_ENDPOINT/sessions/dummy-id")"
```

**何をしているか**
[API一覧](../../01_docs/02_sd/02_API設計/API一覧.md) のPhase1対象8API分のルートすべてに対して、HTTPステータスコードだけを取り出して一覧表示します。ルート登録漏れがないことの確認です。

**正常な結果**

```
qualifications       GET  -> 200
categories           GET  -> 200
questions            GET  -> 200
users/me             GET  -> 200
questions/random     POST -> 200
sessions             POST -> 200
sessions/{id}        GET  -> 200
sessions/{id}        PUT  -> 200
```

8行すべて `200` であること。現在の統合先はダミーLambdaなので、リクエストボディの内容は問われません（`403` が返る場合はルートは存在するが権限設定の誤り、`404` はルート未登録）。

**あわせて確認: Phase3のエンドポイントが未登録であること**

```bash
curl -s -o /dev/null -w "questions/import -> %{http_code}\n" -X POST -H "Authorization: Bearer $ID_TOKEN" "$API_ENDPOINT/questions/import"
```

Phase3対象のためルート自体が存在せず、`403` と `{"message":"Missing Authentication Token"}` が返るのが正常です（API Gatewayは未登録パスに対してこのメッセージを返します。トークンの有無とは無関係です）。`200` が返る場合はフェーズ先行実装になっているため取り下げが必要です。

## STEP 8: CORS設定を確認する

**コマンド**

```bash
curl -i -X OPTIONS -H "Origin: http://localhost:5173" -H "Access-Control-Request-Method: GET" "$API_ENDPOINT/qualifications"
```

**何をしているか**
ブラウザがクロスオリジンのリクエスト前に自動送信する「プリフライトリクエスト」を手動で再現しています。フロントエンド（Step 4）からAPIを呼べるかどうかがここで決まります。

**正常な結果**

```
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: http://localhost:5173
Access-Control-Allow-Methods: GET,POST,PUT,OPTIONS
Access-Control-Allow-Headers: Content-Type,Authorization
```

`Access-Control-Allow-Origin` に指定したオリジンがそのまま返ること。

**補足: 許可外オリジンの挙動**

```bash
curl -s -D - -o /dev/null -X OPTIONS -H "Origin: https://evil.example.com" -H "Access-Control-Request-Method: GET" "$API_ENDPOINT/qualifications" | grep -i "access-control-allow-origin"
```

この場合も `204` は返りますが、`Access-Control-Allow-Origin` には **リクエスト元とは異なるオリジン**（許可リストの先頭 `http://localhost:5173`）が返ります。ブラウザは返ってきた値と自分のオリジンを突き合わせて一致しなければ通信を破棄するため、これが正しくブロックされている状態です。ワイルドカード `*` が返っていないこと（API共通設計 §9）を確認してください。

なお、プリフライト（`OPTIONS`）自体には認証がかかりません。ブラウザは仕様上プリフライトに `Authorization` ヘッダを付けないためで、応答はCORSヘッダのみを返すモック統合であり、データアクセスは一切発生しません。

## STEP 9: アクセスログが出力されていること

**コマンド**

```bash
export MSYS_NO_PATHCONV=1
aws logs tail /aws/apigateway/oracle-master-app-dev --since 15m --format short
```

**何をしているか**
API Gatewayのアクセスログを直近15分ぶん表示します。ログ・監視設計 §1 で定めた項目（メソッド・パス・ステータス・レイテンシ・呼び出しユーザー）が実際に記録されているかを確認します。1行目はGit Bashのパス自動変換を止めるためのもので、前提の項ですでに実行済みなら不要です（Linux/macOSでも実行して害はありません）。

**正常な結果**

これまでのSTEPで叩いたリクエストが1行ずつJSONで出力されます。

```json
{"requestId":"...","httpMethod":"GET","path":"/dev/qualifications","status":"401","responseLatency":"5","userSub":"-"}
{"requestId":"...","httpMethod":"GET","path":"/dev/qualifications","status":"200","responseLatency":"120","userSub":"xxxxxxxx-xxxx-..."}
```

- 401のレコードでは `userSub` が `-`（未認証のため識別子なし）
- 200のレコードでは `userSub` にUUIDが入る
- **メールアドレスがログに出ていないこと**（ログ・監視設計 §1.2 の個人情報の取り扱い）

Lambda側のログも確認する場合:

```bash
aws logs tail /aws/lambda/oracle-master-app-dev-placeholder --since 15m --format short
```

ロググループの実名を確認したい場合:

```bash
aws logs describe-log-groups --log-group-name-prefix /aws/apigateway/oracle-master-app --query "logGroups[].logGroupName" --output text
```

## STEP 10: 後片付け

**コマンド**

```bash
aws cognito-idp admin-delete-user --user-pool-id "$USER_POOL_ID" --username test-m1@example.com
unset ID_TOKEN
```

**何をしているか**
確認用に作ったユーザーを削除し、シェルに残っているトークンを破棄します。テストユーザーを残しておくとCognitoの月間アクティブユーザー数に計上されるため、確認が終わったら消しておきます。

**正常な結果**

出力なし（終了コード0）。削除確認:

```bash
aws cognito-idp list-users --user-pool-id "$USER_POOL_ID" --query "Users[].Attributes[?Name=='email'].Value" --output text
```

何も表示されなければ削除完了です。

## トラブルシューティング

| 症状 | 原因 | 対処 |
|---|---|---|
| STEP 0 で `CLIENT=` が空 | 確認用クライアント追加後のデプロイが未実施 | `npx cdk deploy -c env=dev OracleMasterApp-dev-Auth` を実行 |
| STEP 5 で `None` が返る | パスワード誤り、またはクライアントIDがSPA用になっている | `$CLI_CLIENT_ID` が `oracle-master-app-cli-test-dev` のIDか確認 |
| STEP 5 で `NotAuthorizedException: Incorrect username or password` | `$TEST_PASSWORD` がSTEP 4 と違う値、またはコマンド中のプレースホルダを置換せずに実行した | `echo "文字数: ${#TEST_PASSWORD}"` で確認し、STEP 4 からやり直す（ユーザーの再作成は不要） |
| STEP 5 で `InvalidParameterException: Missing required parameter PASSWORD` | `$TEST_PASSWORD` が空。`read` の案内文の位置にパスワードを書いてしまった場合に起きる | `read` を実行後、カーソルが止まった状態でパスワードをタイプしてEnter。`echo "文字数: ${#TEST_PASSWORD}"` が0以外になることを確認 |
| STEP 5 で `InvalidParameterException: USER_PASSWORD_AUTH flow not enabled` | SPA用クライアントIDを指定している | 確認用クライアントIDを使う |
| STEP 6 で 401 | トークンの有効期限（1時間）切れ | STEP 5 を再実行してトークンを取り直す |
