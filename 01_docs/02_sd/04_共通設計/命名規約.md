# 命名規約

本基本設計書一式および今後のPhase2/3の設計追加時に一貫性を保つための命名規約。

## 1. ドキュメントID

| 対象 | ID形式 | 例 | 採番規則 |
|---|---|---|---|
| 画面 | `S-NN`（2桁連番） | S-01, S-02 | 要件定義書§4.1のIDを継承。新規画面追加時は末尾に連番を追加（欠番を詰めない） |
| API | `API-NN`（2桁連番） | API-01 | エンドポイント一覧の掲載順に採番。エンドポイント自体の識別は必ずHTTPメソッド+パスで行う |
| テーブル/エンティティ | `T-NN`（2桁連番） | T-01 | 要件定義書§6.1のテーブル掲載順に採番 |

## 2. DynamoDB命名規約

| 対象 | 規則 | 例 |
|---|---|---|
| テーブル名 | 環境プレフィックス + `OR_{テーブル種類}_{テーブル名}` | `dev-OR_M_QUESTION`, `prod-OR_T_EXAM_SESSION` |
| 属性名 | camelCase | `qualificationId`, `correctCount` |
| GSI名 | `{属性名}-index` | `qualificationId-index` |
| ID属性値 | UUID v4（`qualificationId`のみ資格コード文字列） | `q1e2f3a4-...` |

### 2.1 テーブル名の構成

```
{環境プレフィックス}-OR_{テーブル種類}_{テーブル名}
   dev / stg / prod        M / T / W       UPPER_SNAKE_CASE（単数形）
```

| 要素 | 規則 |
|---|---|
| 環境プレフィックス | `dev-` / `stg-` / `prod-`。CDKのスタックパラメータから付与する（[システム構成・環境設計](システム構成・環境設計.md) §3） |
| `OR` | 本アプリ（Oracle Master 資格問題アプリ）を示す固定の接頭辞 |
| テーブル種類 | `M`=マスタテーブル / `T`=トランザクションテーブル / `W`=ワークテーブル |
| テーブル名 | UPPER_SNAKE_CASE・**単数形**。複合語はアンダースコアで区切る（`EXAM_SESSION`, `ANSWER_HISTORY`）。種類記号で表現済みの `MASTER` 等の接尾辞は付けない |

### 2.2 テーブル種類の判断基準

| 種類 | 定義 | 該当テーブル（Phase 1） |
|---|---|---|
| `M`（マスタ） | 事前に登録され、利用者の操作によって日常的には増減しない参照データ | `OR_M_QUALIFICATION`, `OR_M_CATEGORY`, `OR_M_QUESTION`, `OR_M_CHOICE`, `OR_M_USER` |
| `T`（トランザクション） | 利用者の操作に伴って継続的に発生・蓄積される業務データ | `OR_T_EXAM_SESSION`, `OR_T_ANSWER_HISTORY` |
| `W`（ワーク） | 一時的な中間データを保持するテーブル。処理完了後は不要となる（TTL等で削除） | Phase 1では該当なし（Phase 3のAI問題生成プレビュー保持等で採用を検討） |

### 2.3 論理エンティティ名との対応

要件定義書 §6 の論理エンティティ名と物理テーブル名の対応は [テーブル一覧](../03_データベース設計/テーブル一覧.md) を参照。設計書本文・API設計書中でテーブルを指す場合は、物理テーブル名（`OR_M_QUESTION` 等）で統一して記載する。

### 2.4 共通項目（監査項目）

全テーブルに以下4項目を必ず設定する。詳細な設定規則は [テーブル一覧](../03_データベース設計/テーブル一覧.md) §共通項目を参照。

| 論理名 | 属性名 | 型 | 説明 |
|---|---|---|---|
| 登録日 | `createdAt` | String | レコード作成日時（ISO 8601, UTC） |
| 登録者 | `createdBy` | String | レコードを作成した主体の識別子 |
| 更新日 | `updatedAt` | String | レコード最終更新日時（ISO 8601, UTC）。作成時は `createdAt` と同値 |
| 更新者 | `updatedBy` | String | レコードを最後に更新した主体の識別子。作成時は `createdBy` と同値 |

## 3. API命名規約

| 対象 | 規則 |
|---|---|
| パス | 複数形リソース名（`/questions`, `/sessions`）。個別リソースは `{resourceId}` パスパラメータ |
| クエリパラメータ | camelCase（`qualificationId`, `nextToken`） |
| エラーコード | UPPER_SNAKE_CASE（`VALIDATION_ERROR`） |

詳細は [API共通設計](../02_API設計/API共通設計.md) を参照。

## 4. フロントエンド命名規約（参考・詳細設計で確定）

- コンポーネント名: 画面IDに対応する形（例: `S05OutputSettingPage` 等）を目安とし、詳細はフロントエンド詳細設計で定める。
- 本基本設計書では、画面ID（S-01〜S-09）・API ID（API-01〜API-10）・テーブルID（T-01〜T-07）を横断的な参照キーとして使用する。

## 5. Phase表記

- 「Phase 1」「Phase 2」「Phase 3」の表記は要件定義書§2.1, §11の定義に統一する。
- Phase 3実装だが Phase 1/2 でUI上のみ存在する画面・APIには、各ドキュメントの見出し直下に注意書き（例: 「本設計はインターフェース定義のみ。Phase1・Phase2では未実装」）を明記する（[S-04](../01_画面設計/個別画面設計書/S-04_問題作成インポート画面.md), [API-05](../02_API設計/個別API設計書/API-05_問題インポート.md), [API-06](../02_API設計/個別API設計書/API-06_AI問題生成.md) 参照）。
